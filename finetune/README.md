# Fine-tuning the copy generator

A LoRA adapter on Qwen2.5-0.5B-Instruct, trained on 51 hand-written examples of
noszn's voice, served behind an OpenAI-compatible endpoint so the app's existing
LLM gateway can talk to it without a single line changing.

**It is off by default, and it should be.** The voice transferred. The facts
did not. See [What it can't do](#what-it-cant-do).

## Running it

```bash
python -m venv .venv-ft && .venv-ft/bin/pip install -r finetune/requirements.txt
```

```bash
cd finetune && python build_dataset.py && python train.py && python evaluate.py
```

About five minutes on an M-series Mac. The adapter lands in `adapters/` and is
gitignored — it's 44 MB and rebuildable from the recipe.

To serve it:

```bash
cd finetune && python serve.py
```

Then point the copy generator at it and start the API as normal:

```bash
COPY_LLM_BASE_URL=http://localhost:8100/v1 COPY_LLM_MODEL=noszn-voice uvicorn app.main:app
```

Leave `COPY_LLM_BASE_URL` blank and the copy generator uses the main model, which
is the default and the recommendation.

## The data

51 examples across six kinds of copy — product descriptions (25), email subject
lines (10), restock notices (6), win-backs (4), care instructions (3), sizing
notes (3). All hand-written, none generated by a model, because the point was to
capture a voice and a model asked to imitate a voice will produce the average of
its training data instead.

`build_dataset.py` splits them 40/11 stratified by kind, so the held-out set has
at least one of each rather than eleven product descriptions by luck.

## What it does well

Eleven held-out prompts, base against tuned, same decoding, same brief. Only the
adapter differs.

|                        | base | tuned | tuned @0.4 |
| ---------------------- | ---: | ----: | ---------: |
| banned words / gen     |  0.0 |   0.0 |        0.0 |
| capitalised lines      |   20 |     0 |          0 |
| stray script (gens)    |    0 |     0 |          0 |
| avg words              | 52.2 |  16.5 |       16.0 |

The third column samples at temperature 0.4, which is what `app/copywriter.py`
actually runs at. Greedy decoding is the honest way to compare two models, but it
isn't what ships, and a metric that only passes under settings you don't use is
not a metric.

The length and casing results are the real ones. The base model writes 52 words
with headings and a numbered list; the tuned model writes 16 lowercase words and
stops. That's the voice, and it transferred.

**The banned-words row is a null result.** Both score zero. The base model was
never going to write "elevate your wardrobe" *here*, because the prompt tells it
not to and it obeys. The metric was designed before the numbers came in and it
measured nothing. Reporting it as a win would be dishonest; it's kept in the
table because a null result is a result.

## What it can't do

The 0.5B model invents product facts, and no amount of prompt work fixed it.
Generated through the app, against real products:

- "the hoodie that goes on you" — for a **tee**
- "cargo pant in grey that goes with everything" — the product is **black**
- "ribbed cotton" — the cargo pant is **ripstop**
- "ready in 24 hours" — an invented delivery promise
- "washed in the wash thatasctimebs everything else" — not words

For a feature whose entire job is describing real garments, that's disqualifying.
Wrong fabric on a product page is a returns problem, and an invented delivery
promise is a complaint.

One thing did improve. Served the app's original prompt — a 19-line tone spec and
a labelled `Product / Type / Price / Tags` block — the adapter dropped an Arabic
word into the middle of an English sentence. It was trained on a two-line brief
and a one-line list of facts, so the app was handing it a prompt shape it had
never seen. `app/copywriter.py` now sends the training format when it's routed to
the adapter, and the stray-script faults went away. A fine-tuned model has its
own prompt contract; it doesn't inherit the one written to steer a general model.

The fact invention survived that fix, which is what makes it a model-capacity
problem rather than a prompting one.

## What would fix it

In rough order of cost:

1. **A bigger base.** 7B, same adapter recipe. Most likely to work — the voice
   transferred fine at 0.5B, so it's the world knowledge and instruction-following
   that's short, and that's what scale buys.
2. **More data.** 51 examples is small. 300 would help, but probably with the
   length and rhythm rather than with inventing fabrics.
3. **Constrain the output.** Have the model fill a template rather than write
   prose, so the fabric and colour are substituted in and never generated.

Option 3 is the one that makes the feature shippable at 0.5B, and it's also the
one that gives up most of the reason to fine-tune in the first place.

## Why it's wired up anyway

The adapter is a genuinely different provider — different model, different
prompt contract, chat-only, no embeddings. Pointing the app at it was a real test
of whether the gateway in `app/llm.py` is provider-agnostic in fact or only in
the README:

```
$ LLM_BASE_URL=http://localhost:8100/v1 LLM_MODEL=noszn-voice python -m app.check_provider
provider : http://localhost:8100/v1
model    : noszn-voice
ok    completion  'ready'
ok    streaming   'ready'
note  no embeddings here - chat only, which is fine
```

Completion and streaming both went through the gateway unchanged. The copy
generator takes its own base URL rather than switching the global one, because
everything else in the app — the copilot, semantic search, sentiment — still
needs a general model and an embedder.
